# 09. 다음 작업과 인수인계

## 9.0 확정 계획 (Owner 확정 2026-08-18 밤 — 이 순서대로 간다. 바꾸면 여기 먼저 고친다)

### 9.0.1 목표와 "쓴다"의 정의

목표: 엔진이 "없다"만이 아니라 **"이제 이걸 이렇게 하라"**를 체계공학 근거(정본 인용)와 함께 답하고, 그 답을 서브 에이전트와 팀원이 MCP로 받아 움직이게 한다.

| 이정표 | 뜻 | 조각 |
| --- | --- | --- |
| M1 | Owner가 "이제 뭐 해야 해?"라고 물으면 위치·부족·다음 3개(왜·어떻게·근거·담당)가 나온다(스크립트) | A1~A3 |
| M2 | 팀원·AI 비서가 MCP로 묻고 답하고, 밤에 자동으로 돈다 | B1~B3 |
| M3 | 새 과제도 하루 안에 같은 답 | C1~C2 |
| M4 | "제대로 됐냐"·"잘 하고 있냐"·"어떻게 판단할까"까지 | D1~E1 |

### 9.0.2 원칙 (변하지 않는 것)

1. 한 번에 한 조각. 조각은 시험·영수증·문서 동기화·commit+push로 닫는다.
2. 판단(A1·A2·D1·D2)은 결정론이고 문서를 직접 읽지 않는다. 안내(A3·E1)는 정본 인용 붙인 안내이며 판단을 바꾸지 않는다.
3. 엔진은 맥락과 벽으로 막혀 있다: 들어오는 것은 **종이 3종**(있음/성숙도 · 내용 상태 · 요구 커버리지)뿐, 나오는 것은 판단 영수증과 mission 후보(→ 지시서)뿐. 맥락 → 엔진은 후보 → 사람 확인 → 관측(규칙이 명확한 03_Out만 자동 확정). 엔진 → 맥락은 별도 writer·별도 권한.
4. 규칙·관계·인풋아웃풋은 정본이 말한 것만 인용 위치와 함께. 관행은 `unstated`로 약하게. 우선순위 규정 > 가이드북 > 일반 SE 지침 > 미표기. 덧씌움은 더할 수 있고 정본 것을 지우지 못한다(D45).
5. 새 기초(잠금·계약·store·top-level root)는 더 만들지 않는다. 밖에서 부르는 문은 MCP 하나(9.1A).

## 9.1A 출시 형태 (Owner 결정 2026-08-18)

- **밖에서 엔진을 부르는 정문은 MCP 하나다.** 팀원·AI 비서·Owner 모두 MCP로 묻고(판단·결손·불명), 답·관측도 MCP로 넣는다. 터미널 CLI 제품은 만들지 않는다(다른 회사 개발자에게 공급할 때만 껍질로 추가 검토).
- 지금 있는 스크립트(runner·드라이버)는 내부용이다: 개발·검증·야간 예약 실행이 치는 것이며 사용자에게 배포하지 않는다. "CLI 배포"라는 별도 산출물은 없다 — 배포되는 것은 엔진 코드 한 벌(운영 체크아웃 최신화)뿐이다.
- MCP 서버는 dev-ERP 안이 아니라 엔진 owner 아래 독립으로 둔다(예: `guild_hall/engineering_engine/mcp/`). dev-ERP는 존폐 미정이므로 엔진 출시 경로가 그것에 의존하지 않게 한다.
- MCP 도구는 로직을 갖지 않고 기존 순수 함수·runner를 그대로 부른다(한 로직, 여러 호출자). 잠금은 하나: launch 파일 + sha 핀 + Owner 동결 grant + zero-write + `_workmeta` 영수증. MCP 활성화 시점·답변 우편함(9.1의 9번)은 Owner 결정.
- 밤에는 예약 실행이 같은 runner를 부른다(엔진용 예약은 아직 미설정).

## 9.1C 실제 사용 장면 (엔진이 지금 실제로 내는 답으로, 2026-08-18)

MCP는 문일 뿐이고, 아래 답은 오늘 KVDS(P26-014)에 실제로 돌린 결과다. 도구 지도의 "밤마다 돌려줘"는 엔진 기능이 아니다 — 예약 실행은 운영 스케줄러(운영 체크아웃의 예약 작업)가 판단 도구를 부르는 것이며, 엔진 안에는 시계가 없다. 9.1B의 7 운영 행은 그렇게 읽는다.

**장면 1 — 착수 직후, 아무 자료도 없을 때.** 사람: "새 과제인데 뭐부터 해?" → 비서가 단계 기대·순서 도구를 부름 → 엔진(② 방사청 + LIG, 관측 0, SRR):
> 바로 시작(19): **체계요구사항명세서[규정·핵심]** → 상호운용성 확보계획서 → M&S 활용계획서 → 예비 TEMP → RAM 계획 → SRR 회의록 → SDP → 기술검토회의 자료 → WBS → (가이드북) 기능분석/할당·이해관계자 기대·형상관리계획·QAP·착수회의록·위험목록·SEMP·TEMP → (발주처) Q1·Q2
> 그 뒤(3): ICD ← SEMP / 기술검토 수행 ← 소요요구서 / FCI ← 소요요구서
(같은 등급 안은 아직 가나다순이 남아 있고, 규정 순서 문장 60줄이 확인되면 등급이 올라간다.)

**장면 2 — 진행 중 과제, "이제 뭐 해야 해?".** 사람: "KVDS CDR 이제 뭐 해야 해?" → 비서가 다음 할 일 도구를 부름 → 엔진:
> 위치: 요구 27건 — 충족 5 · 결손 4 · 불명 18
> 부족: HDD·HRS·SRS·STP 결손(없음 확인됨) / 핵심부품 성적서·DBDD·ICD… 불명(아직 안 봄)
> 다음 할 일 1) 핵심부품 공인시험 성적서 — 왜: 규정이 요구(방위사업관리규정 제79조①⑤⑥·제81조③6), 있어야 함 / 산출: 성적서 / 담당: 검증·품질(qa_reviewer) / 기한: —
> 2) DB 설계기술서(최종) — 왜: 가이드북 권고(2017 p.35·77, 2024 p.82) / 어떻게: 양식 "산출물 목록 참조" / 담당: SW
> 3) ICD 최종 — 왜: 규정 요구 / 담당: 체계
> 그 뒤: 기술검토회의 수행 ← HDD·HRS·ICD·IDD·SDD·SRS
(약점 그대로 보임: "왜"가 규칙 문장이고 "어떻게"가 양식 이름뿐. 이건 조언 lane·양식 라이브러리 몫.)

**장면 3 — 팀원이 문서를 올렸을 때.** 팀원이 `120_CDR/131_자재명세서(Q-BOM)/03_Out/`에 `K-VDS_BOM_260818_v1.1_….xlsx`를 넣음 → 눈 도구: 폴더 131=BOM, 이름에 BOM → **자동 확정**, 관측 "CDR의 BOM 있음(해시 …)" → 다음 판단에서 BOM 불명→충족. 반대로 `139_CDR_회의록및조치결과/03_Out/`에 도면 PDF 93장이 있으면: 폴더는 회의록인데 이름은 도면 → 확정 안 하고 **확인표 + 청소 알림 "엉뚱한 자료"**.

**장면 4 — Owner가 확인표를 볼 때.** 사람: "폴더 확인표 줘" → 15줄: `120_CDR / 131 Q-BOM / bom / 03_Out 1개 / 확인[ ]` … Owner가 체크 → 그 폴더 후보 2,355건이 관측이 됨 → 판단 재실행 → 불명 95 갈림. (아직 아무도 체크하지 않아 엔진은 관측 4개로 돌고 있다.)

**장면 5 — "그건 해당 없음"이라고 답할 때(아직 없음, B2).** 사람: "M&S 활용계획서는 이 과제엔 해당 없어, 시뮬레이션 항목이 SOW에 없음" → 답 도구가 "누가·언제·무엇에·근거"를 기록 → 다음 판단에서 그 항목은 불명이 아니라 해당없음(근거 있음)으로 나오고 같은 질문을 반복하지 않음. 지금은 이 답을 관측 파일에 손으로 적어야 한다.

**장면 6 — 다른 발주처·다른 사업유형.** 사람: "탐색개발 과제인데 SRR 뭐 있어야 해?" → 지금은 **정직하게 "탐색개발 스펙은 초안이라 답 못 함"** 이 맞는 답이다(D43). 체계개발이 아닌 사업유형과 LIG 외 발주처는 스펙·덧씌움이 만들어진 뒤에야 같은 답이 나온다.

## 9.1D 운영 개념 두 가지 (Owner 논의 2026-08-19 아침)

**(1) 눈은 "후보를 묻는 것"이 아니라 "등록 대장을 대조하는 것"으로 간다.**
- 정식 통로는 등록 하나다: 팀원이 03_Out에 넣거나, MCP·메일로 "이 파일은 HDD 최종본"이라고 붙여 들어오면 그 순간 관측이 된다(등록 = 저장). 앞으로 작업 PC는 따로 있고 Soulforge 작업공간에는 엔진이 받은 파일만 저장되므로 파일이 흩어질 일 자체가 줄어든다.
- 훑기(전체 walk)는 후보 확인표를 사람에게 내밀지 않는다. 기본 출력은 **미등록 알림**(폴더별 "등록 안 된 파일 N개")과 청소 알림뿐이며 판단에는 영향 0이다. 엔진 답은 등록된 것 기준으로 "없다"라고 말하고 옆에 "이 폴더에 미등록 파일 12개 — 등록하거나 정리하세요" 한 줄을 붙인다. 후보를 하나하나 묻는 혼란을 없앤다.
- 후보 확인표는 규칙 없이 쌓인 과거 자료를 처음 적재할 때만(KVDS 15개 폴더 1회) 쓰고, 그 뒤 기본 모드에서는 끈다.
- 훑기 주기: 착수 때 1회 + 판단 실행 전 안전망(주 1회) — 등록 대장 ↔ 실제 파일(사라짐·바뀜·미등록) 대조. 증분(바뀐 것만)과 "03_Out만" 모드는 만들 것.

**(2) 사람은 엔진 MCP에 직접 묻지 않는다 — 그 위에 비서 층이 있다.**
- 엔진 MCP(B1)는 결정론 도구 13개다: 규칙·관측·판단·순서·카드. "지금 어디쯤?", "이제 뭐 해야 해?"에 대한 엔진의 답은 **체계공학 순서상 무엇이 있고 없나**까지이며, 기한·발주처 요청·담당·결정 같은 맥락은 모른다.
- 사람이 말을 거는 상대는 **비서 층**(LLM 기반: Codex/Claude 비서 + 맥락 원장 접근)이다. 비서가 엔진 MCP 도구와 맥락 도구(메일·일정·결정·담당)를 같이 불러 답을 조립한다: "CDR이 5/22인데 HDD가 없다(엔진 판단) → 담당 ○○, 발주처가 STD도 추가 요청(맥락)". 답 안에서 **어디까지가 엔진 판단이고 어디부터가 비서의 맥락 읽기인지 표시**한다(판단 불변 원칙).
- 그러므로 엔진 MCP는 얇고 결정론으로 남고, 맥락 이해·조합·말투는 비서 층의 일이다. 비서 층이 밖으로 자기 MCP를 낼지는 나중 결정(다른 클라이언트가 필요할 때). 관련 정본: `docs/architecture/workspace/SE_ASSISTANT_OPERATING_MODEL_V0.md`.

## 9.1E 엔진 입장의 MCP 용어 (2026-08-19 — 비서 층·맥락은 뺀, 엔진이 받고 주는 것만)

| 다음 할 일 `next_steps` / 지시서 | 체계공학 순서상 위치·부족·다음 3개(왜·어떻게·근거·담당). 기한·담당자·발주처 요청은 **비어 있음**(맥락 몫) | 있음 |
| 엔진 질문 목록 `context_requests` | 엔진이 답을 기다리는 항목(불명 = 질문) | 없음(영수증에서 조립 가능) |
| 영수증 재현 `audit_replay` | 같은 입력 → 같은 바이트 | 수동만 |

**벤치마크로 더 넣기로 한 것(2026-08-19, 부록 A; 엔진 입장, 순위순)**: ① 엔진 상태 `engine_status`(버전·규칙판·스위치·프로필·영수증 경로·허용 폴더, 인자 없음) ② 변경 이후 `changes_since`(시각/run 이후 등록·확정·철회·판정 변화·해시 변화; 엔진은 훑은 시점만 앎) ③ `project_status` 보강(현재 단계 한 줄+근거, 단계별 개수·비율, 다음 단계로 못 가는 이유) ④ 항목 보기 `artifact_get` ⑤ 찾기 `rules_find`/`ledger_find`(키워드·단계·updated_since) ⑥ 리소스(`engine://rules/{stage}`·card·manual·profile·release·changelog + subscribe/list_changed) ⑦ 표준 질문 프롬프트 4개 ⑧ 계획 도구 같은 규격(`audit_replay`·`answer_record`·`context_requests`·`observe_amend` dry_run·destructiveHint) ⑨ 기준선 `baseline_set/get`(나중) ⑩ `binding_set`+흔들림 표시(나중) ⑪ 위생: 주석 정직화, 쓰기 꺼짐이면 쓰기 도구 숨김+list_changed, 인자 오류는 isError, 큰 결과 cursor/limit, 모든 결과에 schema_version. 넣지 않는 것: 사람 알림 발송·자유 코멘트·자연어 검색·일정·결재 흐름·문서 저술·삭제 도구·원격 멀티유저 문(비서 층 또는 밖).

**폴더 정리의 원칙(엔진이 폴더를 관리할 때)**: 사람은 폴더를 직접 만지지 않는다. 잘못 저장 = 잘못 등록이므로 **등록 정정**으로 고치고, 파일 이동은 엔진 writer가 대장 기준으로 한다(권한·영수증). 훑기가 낸 미등록·청소 알림도 사람이 폴더에서 처리하는 게 아니라 등록/정정/삭제 요청으로 처리한다. 대량 잘못 저장이 나면 정정 목록을 한 번에 승인한다. 후보 확인표는 규칙 없이 쌓인 과거 자료의 첫 적재 1회용이다.

## 9.1F 접근 권한 모델 (Owner 요구 2026-08-19: "MCP를 부르는 사람을 보고 자료 접근 권한을 나누고 싶다")

상황: 팀원이 각자 PC에서 Codex 같은 비서로 붙어 일을 받아 간다. Owner는 모든 자료를 볼 수 있지만 계약서·단가 같은 것은 아무나 읽으면 안 된다.

**세 겹으로 나눈다 (겹치게, 하나가 뚫려도 다음이 막게).**

| 겹 | 무엇 | 어디서 | 지금 |
| --- | --- | --- | --- |
| 1 신원(누가) | 팀원은 자기 PC → **원격 문(비서/게이트웨이 층, 로그인·SSO)** → 엔진. 엔진 문 자체는 로컬·비공개로 둔다. 로그인한 사람의 `principal`(누구)과 `role`(역할)이 모든 호출에 붙는다 | 비서/게이트웨이 층(원격, OAuth·SSO는 MCP 표준 방식) | 없음(비서 층 미착수). 엔진 쪽 준비: 쓰기 도구에 `principal` 필수 인자 + 영수증 기록(B1 후속) |
| 2 권한표(누가 무엇을) | 역할 × 자료 등급 × 동작. 역할: Owner·PM·체계·HW·SW·품질·외부(발주처/협력). 자료 등급: ⓐ 공개 규칙(규칙·카드·순서 — 누구나) ⓑ 팀 판단(판단 결과·지시서 — 팀원, 지시서는 자기 역할 것 위주) ⓒ 기밀(계약서·SOW·단가·발주처 원문 — Owner·PM만) ⓓ 개인 첨부(작성자·담당·Owner). 동작: 읽기 / 등록 / 확정·정정·답(Owner·PM). 표는 과제 명부(레지스트리) 옆에 두고 과제별로 덮어쓸 수 있게 | 엔진 프로필/명부의 `접근표`(private) + 규칙 행·문서에 등급 태그(계약문서는 기본 기밀) | 없음 |
| 3 집행(엔진이 실제로 막기) | 모든 도구가 `principal`·`role`을 받아 **결과를 걸러서** 낸다: 항목 보기·등록 현황은 허용 등급만, 지시서는 자기 역할 것만, 기밀 문서는 경로·이름조차 안 냄, 확정·정정·답은 허용된 역할만. 엔진 MCP는 원래 **문서 본문을 내주지 않고 메타데이터·경로만** 내므로 파일 자체는 4번째 겹(파일 권한)이 마지막 방어 | `mcp/` 도구 공통 필터 + 영수증에 누가·무엇을 | 없음(B1 후속에 최소형: principal + 허용표) |
| (4) 파일 권한 | OneDrive/NAS 폴더 권한을 등급대로(계약서 폴더는 Owner·PM만) — 엔진 밖 | 운영 | 지금 방식 그대로 |

**원칙**: 엔진 문은 절대 원격으로 열지 않는다(원격은 비서/게이트웨이 층만). 신원은 비서 층이 확인하고 엔진은 그 신원을 믿되 영수증에 남기고 권한표대로 거른다. 자료 등급 태그가 없는 문서는 기본 **기밀**로 다룬다(fail-closed). Owner는 전권, 외부(발주처·협력)는 ⓐ+자기 관련 ⓑ만.

**만드는 순서**: B1 후속에서 `principal` 인자 + 영수증 + 과제 명부 옆 접근표(최소: 역할→허용 도구·허용 등급) → 도구 결과 필터 → 규칙 행·문서 등급 태그(계약문서 기본 기밀) → 비서/게이트웨이 층 로그인(원격)은 비서 층 착수 때.
