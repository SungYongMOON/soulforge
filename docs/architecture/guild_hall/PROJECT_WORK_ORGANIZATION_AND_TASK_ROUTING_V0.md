# Project Work Organization And TASK Routing v0

## 상태와 목적

이 문서는 모든 Soulforge 프로젝트가 재사용할 수 있는 **프로젝트 조직도,
업무분장, TASK 운영 초안**이다. 상태는 `canon_candidate`이며, 실제 프로젝트
조직이나 TASK 스레드를 생성하는 지시가 아니다.

사람에게 보이는 스레드 제목에는 프로젝트 코드 대신 owner가 승인한
public-safe 한글 표시명을 사용한다. 프로젝트 코드, 사람 이름, 실제 업무,
런타임 식별자는 승인된 private metadata가 소유한다.

## 근거와 주장 한계

이 초안은 다음 공식 자료의 시스템공학·품질관리 원칙을 프로젝트 운영 형태로
옮긴 것이다.

- [ISO/IEC/IEEE 15288:2023 개요](https://www.iso.org/standard/81702.html)
- [ISO 9001:2015 프로세스 접근법 안내](https://www.iso.org/files/live/sites/isoorg/files/archive/pdf/en/iso9001-2015-process-appr.pdf)
- [ISO 품질경영 원칙](https://www.iso.org/quality-management/principles)
- [NASA SE Handbook 2.0 시스템공학 기초](https://www.nasa.gov/reference/2-0-fundamentals-of-systems-engineering/)
- [NASA SE Handbook 2.4 Verification과 Validation 구분](https://www.nasa.gov/reference/2-4-distinctions-between-product-verification-and-product-validation/)
- [NASA SE Handbook 4.0 시스템 설계](https://www.nasa.gov/reference/4-0-system-design-processes/)
- [NASA SE Handbook 5.0 제품 실현](https://www.nasa.gov/reference/5-0-product-realization/)
- [NASA SE Handbook 6.0 교차 기술관리](https://www.nasa.gov/reference/6-0-crosscutting-technical-management/)

다만 이 문서는 ISO 적합성·인증, 조항별 충족, 특정 직책의 겸임 금지, 또는
현재 프로젝트가 필요한 증거를 이미 갖췄다는 판정을 하지 않는다. TASK의
4가지 논리 역할과 시작·변경·완료 gate는 공식 원칙을 실무에 적용한
출처로 뒷받침된 합성이며, 표준이 정확히 네 직책을 의무화한다는 뜻이 아니다.

## 실행 authority 경계

이 문서는 조직 역할과 Codex 조정 절차만 정의한다. Task Engine/AX의 업무·분장
후보 생성, 승인·적용, 수행 agent 후보와 accepted assignment 이후 실행 흐름은
다음 정본을 따르며 여기서 다시 정의하지 않는다.

- `../workspace/PROJECT_TASK_ENGINE_LIFECYCLE_V0.md`
- `../foundation/DEVELOPMENT_ROADMAP_V0.md`

프로젝트 총괄 CEO/업무운영·팀장은 목표·우선순위·책임 경계와 불명확한 분류를
판단한다. Codex 팀장 스레드는 이 정책을 적용하는 지속형 조정 surface일 뿐,
위 정본의 Task Engine authority를 대체하지 않는다.

이 프로젝트 조직 계약은 프로젝트 귀속이 확인된 업무에만 적용한다. `[SYSTEM]`,
AX, ERP의 비프로젝트 업무는 각 owner의 기존 routing을 유지하고, `COMMON`의
회사·팀 운영 업무는 `COMMON_TEAM_OPERATIONS_AND_ROUTING_V0.md`를 따른다.
비프로젝트 업무에 프로젝트 조직을 억지로 배정하지 않는다. 공통 위임 패킷을
사용할 때 프로젝트 확장 필드가 해당되지 않으면 값을 생략해 추정하지 않고
명시적으로 `not_applicable`로 기록한다.

프로젝트 manager와 COMMON·AX·ERP·SYSTEM manager는 서로 다른 sibling branch의
owner다. branch를 넘는 메시지는 `협업 요청`, `검토 요청`, `재분류 요청`으로
구분하며, 요청을 보낸 manager가 수신 branch의 상급자가 되거나 domain authority를
가져오지 않는다.

## 사람에게 보이는 조직도

```text
[프로젝트명] 총괄 CEO/업무운영·팀장
├─ [프로젝트명] 시스템공학·요구사항/책임자
├─ [프로젝트명] 하드웨어설계/책임자
├─ [프로젝트명] 소프트웨어설계/책임자
├─ [프로젝트명] 기구설계/책임자
├─ [프로젝트명] 전장·인터페이스통합/책임자
├─ [프로젝트명] 시험·검증/책임자
├─ [프로젝트명] 품질·인증/책임자
├─ [프로젝트명] 형상·변경관리/책임자
├─ [프로젝트명] 기술자료·데이터관리/책임자
├─ [프로젝트명] 구매·자재재고/책임자
├─ [프로젝트명] 일정·계약대외협력/책임자
├─ [프로젝트명] 안전·보안보증/책임자
├─ [프로젝트명] 생산·정비지원/책임자
├─ [프로젝트명] 원가·예산/책임자
└─ [프로젝트명] 홍보·대외공개/책임자
```

위 15개 책임 분야는 모든 프로젝트에 공통으로 존재하는 **업무 분류
surface**다. 실제 규모가 작으면 한 사람이 여러 분야를 맡을 수 있지만,
각 업무에서 어떤 책임으로 행동했는지는 구분해서 기록한다.

TASK 스레드는 영구 조직이 아니다. 새 결과물이나 다단계 실행을 끝낼 때까지
필요한 임시 실행 단위이며, 정확히 한 분야를 주관으로 둔다.

## 업무분장 규칙

1. 프로젝트 총괄 CEO/업무운영·팀장이 업무를 먼저 분류한다.
2. 한 업무의 `주관 책임자`는 정확히 한 분야다. 다른 분야는 `협업` 또는
   `검토`로 구분한다.
3. 분야 책임자는 자기 범위 안이면 `수락`한다. 범위 밖이면 수행하지 않고
   `사유 + 적절한 주관 후보`를 포함한 재분류 요청으로 반환한다.
4. 주관 후보가 없거나 후보가 충돌하거나 프로젝트 귀속이 불명확하면 총괄
   CEO/업무운영·팀장에게 에스컬레이션한다.
5. 기술 판단, 실행, 독립 검토, 사람의 수락·승인은 같은 의미가 아니다. TASK에
   필요한 역할을 따로 기록한다.
6. 분류 수락은 실제 사람 배정, 외부 전송, 구매·지급, 계약 변경, 기준선 승인,
   공개 또는 최종 수락을 자동으로 허가하지 않는다.

분장안의 최소 기록 형식은 다음과 같다.

```text
업무 → 프로젝트 귀속 → 주관 책임자 → 협업 → 독립 검토
     → 수락·재분류·에스컬레이션 → 근거 → 확신도 → TASK 판단
```

## TASK의 4가지 논리 역할

| 논리 역할 | 책임 |
| --- | --- |
| 책임 owner | 목표·범위·완료 기준을 지키고, 정확히 한 주관 분야를 대표한다. |
| 수행자/에이전트 | 승인된 입력과 범위 안에서 결과물과 실행 근거를 만든다. |
| 독립 검토자 | 결과를 만든 사람과 분리된 관점에서 기준·근거·결함을 확인한다. 필요한 독립성 수준은 위험도에 맞춘다. |
| 수락·승인자 | 결과가 목적과 승인 기준을 충족했는지 수락한다. 외부 약속·지출·기준선·공개의 경우 사람 owner 권한이 필요하다. |

이는 네 명의 고정 인원을 뜻하지 않는다. 저위험 업무에서는 한 사람이 일부
역할을 겸할 수 있다. 다만 자기 결과를 스스로 “독립 검토 완료”라고 표시할 수
없으며, 법규·안전·보안·품질·계약 또는 프로젝트 기준이 더 강한 분리를 요구하면
그 기준을 따른다.

## TASK 생성과 이어쓰기

새 TASK를 만드는 경우:

- 새로운 결과물을 만든다.
- 여러 단계의 실행과 지속 추적이 필요하다.
- 별도 Verification 활동, 별도 Validation 활동, 별도 독립 검토 또는 별도 수락
  판단이 필요하다.
- 기존 TASK와 목표, 주관 책임자, 기준선, 인터페이스 또는 승인 범위가 달라졌다.

기존 TASK에 이어 기록하는 경우:

- 같은 결과물의 작은 수정·보완이다.
- 목표, 주관 책임자, 범위, 기준선, 인터페이스, 승인 범위와 수락 기준이 그대로다.
- 새로운 Verification, Validation, 독립 검토, 수락 판단이나 외부 약속이
  필요하지 않다.

같은 업무의 상태 변경은 새 TASK를 반복해서 만들지 않고 기존 TASK에 기록한다.
상태의 정본과 후보 결정 상태·실행 상태의 분리는
`../workspace/PROJECT_TASK_ENGINE_LIFECYCLE_V0.md`를 따르며 이 문서에서 별도
상태표를 정의하지 않는다. 완료는 실제 근거와 수락 판단이 있을 때만 주장한다.

## TASK gate

### 시작 gate

- 프로젝트 귀속과 업무 목적이 확인됐다.
- 책임 owner와 주관 분야가 정확히 하나다.
- 수행 입력, 적용 기준선, 인터페이스와 제약이 식별됐다.
- 완료 기준, V/V 필요 여부, 독립 검토와 수락·승인 역할이 정해졌다.
- 사람 owner 승인이 필요한 행동과 중단조건이 표시됐다.

하나라도 핵심 값이 불명확하면 `확인대기` 또는 재분류 상태로 두고 실행을
시작하지 않는다.

### 변경 gate

목적, 요구사항, 기준선, 인터페이스, 책임 owner, 수락 기준 또는 외부 약속이
바뀌면 영향 분석과 재분류를 수행한다. 새 결과물·새 독립 검토·새 승인 범위가
생기면 새 TASK로 분리한다. 단순한 같은 범위 보완만 기존 TASK에 이어 쓴다.

### 완료 gate

- 결과물과 실행 근거가 지정 위치에 존재한다.
- 필요한 Verification과 Validation의 목적·기준·증거·판정이 각각 연결됐다.
- 형상·변경·기술자료 상태가 최신이다.
- 부적합, 예외, 미해결 위험, 공급·생애주기 영향이 숨겨지지 않았다.
- 지정된 검토와 수락·승인 근거가 있다.

수행 종료, 에이전트 성공, 파일 존재만으로 완료를 주장하지 않는다.

## 사람 owner 승인 경계

다음은 역할 책임자나 TASK 스레드가 자동으로 확정하지 않는다.

- 실제 사람 담당자와 우선순위의 최종 확정
- 고객·협력사·Slack·메일 등 외부 전송과 공식 약속
- 구매·지급·예산·계약 변경
- 기술 기준선 승인, 최종 수락, 완료 승인
- 안전·보안 영향이 있는 공개와 외부 업로드

승인 근거가 없으면 `제안`, `검토 중`, `확인대기`까지만 표시한다.

## 공개·비공개 경계

- 이 문서에는 역할, 규칙, 필드와 합성 예시만 둔다.
- 실제 프로젝트 목록·코드·사람·업무·근거·스레드 식별자는 private metadata가
  소유한다.
- 메일 본문, 첨부 원문, 개인정보, secret은 업무분장표나 공개 제목에 복사하지
  않는다.
- 이 문서만으로 조직 스레드, TASK, party, automation 또는 default route를
  만들지 않는다.
