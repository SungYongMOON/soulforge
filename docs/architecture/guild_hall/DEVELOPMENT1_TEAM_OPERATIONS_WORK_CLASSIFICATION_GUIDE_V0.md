# 개발1팀 운영실 업무분장·일반업무 분류 가이드 v0

## 상태와 목적

이 문서는 개발1팀 운영실의 상시 책임, 프로젝트와 무관한 업무의 분류,
공통지원 TASK, 정식 프로젝트와 개발1팀 자체 프로젝트의 경계를 한 화면에서
이해하고 적용하기 위한 public-safe 정본 후보다.

상태는 `canon_candidate`다. Owner가 2026-07-30 운영 가이드 기록과 운영실
책임자 구성을 지시했으나, 현재 정본에 남아 있는
`[미할당 프로젝트] 업무운영/팀장`의 퇴역과 기존 route·workflow의 교체는
별도 migration 검증이 필요하다. 이 문서만으로 사람 배정, 구매·지출,
외부 전송, 프로젝트 기준선, 최종 수락 또는 자동 route를 승인하지 않는다.

## 한 문장 원칙

`일반업무`는 업무일지의 보고 묶음일 뿐 책임 조직이 아니며, 실제 업무는
운영실 상시 책임, 공통지원 TASK, 정식 프로젝트, 개발1팀 자체 프로젝트 중
하나로 분류하고 불명확한 상태만 짧게 `분류대기`로 둔다.

│        │  └─ 프로젝트 15개 책임 분야
│        │     └─ 결과물 단위 TASK
│        └─ 개발1팀 자체 프로젝트/팀장
│           └─ 필요한 책임 분야

짧은 상태이며, 공통지원 TASK는 종료조건이 있는 일회성 실행 단위다.

## 역할·프로젝트·TASK·업무일지의 차이

| 구분 | 답하는 질문 | 수명 | 예 |
| --- | --- | --- | --- |
| 상시 책임 `ROLE` | 무엇을 계속 건강하게 유지하는가? | 계속 | 재고 정확성, 시험환경 가용성, 표준 최신성 |
| 프로젝트 `PROJECT` | 어떤 독립 결과를 언제까지 완성하는가? | 목표 달성까지 | 고객 납품장비, 공용 시험치구 개발 |
| TASK | 다음에 닫아야 할 결과물은 무엇인가? | 완료·중단까지 | 재고 실사, 탑재시험 결과서, 장비 수리 |
| 업무일지 `LOG` | 실제로 무엇을 했는가? | 당일 기록 | 자재 목록 대조, 배선 점검 2시간 |

역할 하나가 여러 TASK를 관리할 수 있고, 프로젝트 하나도 여러 TASK를 가진다.
업무일지는 ROLE·PROJECT·TASK의 실제 수행을 기록하지만 새 책임 조직을 만들지
않는다.

## 개발1팀 운영실의 일곱 책임

일곱 책임은 분류와 책임 경계를 분명하게 보이기 위한 상시 책임 surface다.
사람이나 agent가 적으면 한 수행자가 여러 책임을 맡을 수 있지만, 업무마다
정확히 한 주관 책임을 기록한다.

| 책임 | 맡는 업무 | 맡지 않는 업무·인계 | 대표 산출·관리 대상 |
| --- | --- | --- | --- |
| 전략기획·포트폴리오 | 공통 intake, `분류대기`, 공식·자체 프로젝트 구분, 공통 일정·일일업무 집계, 우선순위·capacity·지원공수·운영위험·성과, 통합 개선 backlog | 사람 최종 배정, 프로젝트 기술 판단, 프로젝트 시작·종료와 예산 승인을 확정하지 않는다. | 업무분장표, portfolio 현황, 분류대기·지원공수, 통합 개선 우선순위, 결정 요청 |
| 인력·역량·조직지원 | 역량표, 교육·온보딩, 멘토링, 역할 준비도, 백업 확보, 가용성 신호 | 채용·평가·징계·보상·민감 인사정보를 소유하지 않고 특정 프로젝트 산출물을 대신하지 않는다. | 역량표, 교육계획, 온보딩 체크, 역할 준비도 |
| 경영관리·예산·행정 | 팀 예산계획·사용현황, 비용 가시성, 행정요청, 경영보고, 증빙 누락·기한 확인 | 회계·세무·법무 정본, 지출·예산 증액, 계약 변경을 승인하지 않는다. | 예산·비용 현황, 행정 요청표, 경영보고 후보 |
| 구매·자산·재고 | 공용 구매 요청 흐름, 입고·출고·반납, 자산·공구·소모품·캐비닛 위치·수량·상태 | 프로젝트 BOM의 기술 대체, 공급자 품질 수락, 발주·지출·예산을 승인하지 않는다. | 자산·재고대장, 위치표, 구매·입고·반납 상태 |
| 품질·표준·지식관리 | 공통 SOP·template·표준·검토체계, 형상·변경 원칙, 시험증거 연결, 교훈·검색색인, 표준·절차 개선 후보 발굴 | 프로젝트 결과품질과 기술 기준선, public canon 승격과 통합 개선 우선순위를 대신 승인하지 않는다. | 표준·template 색인, 변경·교훈 목록, 표준·절차 개선 후보 |
| 제작·정비·시험환경 | 시제품 제작지원, 생산이관 준비, 장비 정비, 시험장·수조·계측기 가용성, 교정·점검·안전사용 절차 | 별도 생산조직의 생산 결과와 프로젝트 설계 기준선을 소유하지 않는다. | 장비·시험환경 상태, 점검·교정표, 정비·사용절차 |
| 협업·회의·결정·공지 | Slack 공간·제목·thread 규칙, 회의 준비·회의록, 결정·보류·담당·기한, 승인된 공지와 후속조치 | 회의 개최나 공지 작성 자체를 성과로 보지 않고, 기술·계약·지출·외부공개를 승인하지 않는다. | 회의·결정·공지 색인, 열린 조치, 게시 위치·원문 링크 |

운영실 공통 일정과 일일업무 집계의 단일 주관은 전략기획·포트폴리오다.
협업·회의·결정·공지는 회의 일정, 알림, 결정 후속을 지원하고, 품질·표준·
지식관리는 표준·절차 개선 후보를 발굴한다. 여러 책임에서 나온 개선 후보의
통합 우선순위와 capacity 조정은 전략기획·포트폴리오가 맡는다.

### 책임자 공통 운영 규칙

1. 자기 범위의 업무만 수락한다.
2. 범위 밖이면 수행하지 않고 `사유 + 적절한 주관 후보`로 재분류 요청한다.
3. 한 업무의 주관 책임은 하나이며 나머지는 협업 또는 독립 검토다.
4. 새 결과물·다단계 실행·후속 추적·별도 검토가 필요하면 TASK로 분리한다.
5. 작은 반복 활동은 ROLE 체크리스트나 업무일지로 기록한다.
6. 사람 배정·인사·예산·구매·외부전송·기준선·최종수락은 Owner 승인 경계를
   넘지 않는다.

## 업무 분류

| 코드 | 분류 | 판단 기준 | 결과책임 |
| --- | --- | --- | --- |
| `OPS` | 운영실 업무 | 반복적으로 팀의 상태·능력·환경을 유지한다. | 해당 운영실 책임자 |
| `SUP` | 공통지원 | 다른 팀·조직·프로젝트의 결과에 제한된 범위로 기여한다. | 요청 조직 또는 상위 프로젝트 owner |
| `PRJ-O` | 정식 프로젝트 | 고객·계약·회사 승인·공식 일정·예산·마일스톤이 있다. | 정식 프로젝트 업무운영/팀장 |
| `PRJ-I` | 개발1팀 자체 프로젝트 | 개발1팀이 독립 결과의 통합책임을 맡고 여러 TASK를 관리한다. | 자체 프로젝트/팀장 |
| `TRIAGE` | 분류대기 | 정보가 부족해 위 네 분류를 즉시 고를 수 없다. | 운영실은 분류 완료에만 책임 |

`TRIAGE`는 상시 역할이나 프로젝트가 아니다. v0 운영 시작값으로 다음 주간
분류점검 또는 접수 후 5영업일 중 먼저 오는 시점까지 분류안을 만든다.
시간 기준은 pilot 후 조정할 수 있지만, 무기한 보관하거나 기술 실행을 먼저
시작하지 않는다.

## 분류 순서

```text
업무 접수
  → 이미 정확한 정식 또는 개발1팀 자체 프로젝트가 있는가?
      ├─ 예: 해당 프로젝트 manager로 인계
      └─ 아니오
  → 반복적으로 팀 상태·환경을 유지하는가?
      ├─ 예: 운영실 7개 책임 중 하나
      └─ 아니오
  → 다른 조직의 결과를 제한된 범위로 지원하는가?
      ├─ 예: 공통지원 TASK, 결과책임은 요청 조직에 유지
      └─ 아니오
  → 개발1팀이 독립 결과를 통합 책임지는가?
      ├─ 예: 자체 프로젝트 gate 확인
      └─ 불명확: 분류대기
```

## `일반업무` 기록 규칙

`일반업무`라는 표현은 일일업무일지의 화면 묶음 또는 보고용 상위 제목으로는
유지할 수 있다. 그러나 `일반업무`만 기록하고 실제 귀속을 비워두지 않는다.

최소 기록 형식:

```text
[분류] [귀속] [결과책임] [수행] [ROLE/TASK] [수행결과] [투입시간] [근거]
```

예:

```text
OPS | 구매·자산·재고 | A: 운영실 책임자 | R: 수행자
| ROLE 활동 | 캐비닛 2층 3칸 위치표 갱신 | 1h | 재고대장 pointer

SUP | 요청 프로젝트 | A: 요청 프로젝트 manager | R: 개발1팀 수행자
| TASK | 외산장비 선박 탑재 인터페이스 확인 | 6h | 결과 packet pointer
```

메일·Slack 원문, 개인정보와 private payload는 업무일지나 public 문서에 복사하지
않고 승인된 위치의 metadata pointer만 남긴다.

## 공통지원 TASK

공통지원은 별도 상시 팀장이나 부서가 아니라 필요한 경우에만 만드는 TASK다.

다음 강제 조건 중 하나가 있으면 공통지원 TASK를 만든다.

- 종료조건과 결과물이 있다.
- 기한·후속확인·의존성·인수인계가 있다.
- 고객 약속, 안전 확인, 시험증거 또는 납품 영향이 있다.
- 한 번의 작업 세션으로 끝나지 않는다.

강제 조건이 없다면 다음 세 조건을 모두 만족할 때만 별도 TASK 없이 ROLE 활동
또는 업무일지로 닫을 수 있다.

- 한 번에 끝나고 후속 확인이 없다.
- 다른 사람의 일정·결정·수락에 영향을 주지 않는다.
- 반복 체크리스트로 충분하다.

어느 쪽도 명확하지 않으면 업무운영/팀장이 결과물·위험·의존성·검토 필요성을
확인해 TASK 여부를 정하고, 사람배정이나 승인권한이 필요한 판단은 Owner에게
올린다.

공통지원 TASK에는 요청 조직, 상위 프로젝트가 있으면 그 project ref, 정확히 한
주관 책임, 수행자, 협업, 독립 검토, 수락자, 완료증거와 중단조건을 기록한다.
지원 공수가 늘어도 결과책임이 요청 조직에 남아 있으면 자체 프로젝트로
자동 승격하지 않는다.

## 개발1팀 자체 프로젝트 승격 gate

### 프로젝트 생성 전 제외

다음 중 하나면 새 자체 프로젝트를 만들지 않는다.

- 이미 적절한 정식 프로젝트가 있다.
- 다른 조직이 최종 결과책임을 유지한다.
- 하나의 TASK로 목표·완료·수락을 충분히 관리할 수 있다.

### 필수조건

다음 세 조건을 모두 만족해야 한다.

1. 개발1팀이 통합 결과책임을 가진다.
2. 독립 목표·산출물·종료조건을 한 문장으로 쓸 수 있다.
3. 편입할 적절한 정식 상위 프로젝트가 없다.

### 강제 gate

다음 중 하나라도 있으면 프로젝트 관리 방식을 우선 검토한다.

- 안전·품질·보안·형상·변경 통제가 필요하다.
- 별도 예산·구매·자산·시험장비가 배정된다.
- 여러 팀·외주·시험환경의 일정 의존성이 있다.
- 공식 설계·시험 검토, 승인 또는 인수증거가 필요하다.

### 누적 gate 시작값

다음 중 두 개 이상이면 자체 프로젝트 승격안을 만든다.

- 예상 공수 10인일 이상
- 시작부터 종료까지 4주 이상
- 상호 의존 TASK 3개 이상
- 수행자 2명 이상 또는 두 조직 이상 참여
- 유사 지원 3회 이상 반복
- 다른 프로젝트에서 재사용할 결과물
- 완료 후 유지보수·변경요청 예상
- 기존 프로젝트와 자원 우선순위 충돌

수치 기준은 v0 pilot 시작값이다. 기준을 만족해도 실제 프로젝트 생성·번호·사람
책임자·예산·우선순위는 Owner가 승인한다. 고객·계약·경영진의 공식 약속,
납품일, 대외 시험 또는 공식 예산코드가 생기면 자체 프로젝트보다 정식
프로젝트나 정식 프로젝트 작업패키지를 우선한다.

## 대표 사례

| 업무 | 분류·주관 | 운영 방식 |
| --- | --- | --- |
| 캐비닛 정리, 자재 위치 정상화 | `OPS` 구매·자산·재고 | ROLE 활동 또는 범위가 크면 운영 TASK |
| 정기 재고 실사 | `OPS` 구매·자산·재고 | 반복 체크리스트·주기 TASK |
| 팀원 교육·온보딩 | `OPS` 인력·역량·조직지원 | 교육계획·체크리스트 |
| 특정 프로젝트 시험 하루 지원 | 해당 프로젝트 | 해당 프로젝트 TASK에 수행자로 참여 |
| 타팀 장비 시험 이틀 지원 | `SUP` | 공통지원 TASK, 결과책임은 요청팀 |
| 외산장비 일회성 선박 탑재 | `SUP` 또는 상위 프로젝트 | 탑재·인터페이스·안전·시험 전체 책임을 넘겨받으면 project gate |
| 공용 시험치구 단순 제작 | `OPS` 제작·정비·시험환경 | 단일 운영 TASK |
| 공용 시험치구 설계·제작·검증 | `PRJ-I` 후보 | 여러 TASK·형상·검증이 있으면 자체 프로젝트 |
| 고객 납품장비 개발·시험 | `PRJ-O` | 정식 프로젝트와 15개 책임 분야 |

## 업무분장 기록 형식

```text
업무
→ 요청 원천
→ 분류(OPS/SUP/PRJ-O/PRJ-I/TRIAGE)
→ 귀속
→ 주관 책임자 1명
→ 협업
→ 독립 검토
→ 수행자
→ 수락·승인자
→ TASK 생성·계속·불필요
→ 시작·변경·완료 gate
→ 근거·확신도
→ Owner 승인 필요사항
```

업무분장은 수행 완료나 사람 배정 승인이 아니다. 책임자는 자기 범위와 TASK
필요성을 판단하고, 수행은 별도 TASK와 승인 범위에서 진행한다.

## 기존 `[미할당 프로젝트]` migration 후보

권장 최종 상태는 `[미할당 프로젝트] 업무운영/팀장`을 새 업무에 사용하지 않고
`분류대기`를 운영실 전략기획·포트폴리오 책임 아래의 상태로 흡수하는 것이다.

실제 migration은 다음 순서로 한다.

1. 기존 task의 열린 업무·근거·결정·blocker·TASK ref를 읽기 전용으로 확인한다.
2. 각 항목을 운영실 책임, 공통지원, 정식 프로젝트, 자체 프로젝트 후보로
   재분류한다.
3. 인계 수락을 확인한다.
4. 기존 task의 ID·이력을 삭제하지 않고 archive/retire 후보로 둔다.
5. public 정본, thread-manager workflow, canonical/installed skill, private
   address book과 local binding을 같은 revision 의미로 동기화한다.
6. fresh review와 validator가 통과한 뒤에만 새 intake를 중단한다.

migration 전에는 현행 정본 route와 이 후보 규칙이 충돌하므로 자동 routing을
활성화하지 않는다.

## 사람 Owner 승인 경계

다음은 운영실 팀장이나 책임자가 자동 확정하지 않는다.

- 실제 사람 담당자, 인사·평가·보상과 우선순위 최종 확정
- 구매·발주·지급·예산·계약 변경
- 고객·협력사·Slack·메일·외부 시스템 전송과 공식 약속
- 프로젝트 생성·번호, 기술 기준선, 공개, 최종 수락과 완료 승인

승인 근거가 없으면 `제안`, `검토 중`, `분류대기`, `확인대기`까지만 표시한다.

## 공개·비공개 경계

- 이 문서에는 역할, 분류, 합성 예시와 시작 기준만 둔다.
- 실제 사람·프로젝트 code·업무·자료·thread id·binding은 승인된 private/local
  owner surface가 소유한다.
- 메일·Slack 원문, 첨부, 개인정보, private payload와 secret을 public 문서나
  task 제목에 복사하지 않는다.
- 이 문서만으로 Slack 게시, 구매·발주, 외부전송, automation, party, default
  route 또는 프로젝트 기술 기준선을 만들지 않는다.
